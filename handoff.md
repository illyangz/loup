- **New lib `artifacts/api-server/src/lib/idempotency.ts`:** `withIdempotency(endpointName, handler)` — note this *wraps* the route handler (not a normal `router.use()`-style middleware you chain separately) so it can fully `try/catch` around the handler and control exactly when the response is sent. Behavior: no `Idempotency-Key` header → passes straight through to `handler`, zero behavior change (backward compatible with every existing client, including the current frontend, which doesn't send this header yet). With a key: looks up `idempotency_records` by key; an existing *resolved* row replays its stored `{statusCode, responseBody}` without re-running `handler`; an existing *reserved* row (another request for the same key is still in flight) polls every 50ms for up to ~2s and then replays or 409s; no existing row → inserts a reservation (`statusCode: 0` sentinel), runs `handler`, and **only after the settle write to `idempotency_records` is awaited** does it actually send the real response to the client (captured via a `res.json` override that stashes the body instead of sending immediately). If `handler` throws, the reservation row is deleted (awaited) before the error is rethrown, so a retry with the same key isn't stuck forever behind a dead reservation.
- **Applied to the three endpoints PRPD P1-4 names:** `POST /bookings` (bookings.ts), `POST /billing/pay` (billing.ts), `POST /pack/requests/:id/approve` (pack.ts) — call sites changed from `router.post(path, withIdempotency(name), handler)` to `router.post(path, withIdempotency(name, handler))` (the middleware now owns invoking the handler).
- **Real bug fixed while auditing for this:** `POST /billing/pay` had no check that the statement was still `status: 'open'` before marking it paid — two near-simultaneous requests (double-click, retry) could both mark the same statement paid and both open a fresh statement. Fixed with the same atomic compare-and-swap pattern `pack.ts`'s `claimPendingRequest` already used: `UPDATE statements SET status='paid', ... WHERE id=$1 AND status='open' RETURNING *`; zero rows returned → 409 "This statement was already paid". This is a real duplicate-payment fix independent of the Idempotency-Key feature (protects clients that never send the header too).
- **Provider `/v1/provider/orders/:id/advance` (the ledger-writing "complete a booking" endpoint) was checked and needs no idempotency wrapping** — `writeRedemptionLedger` only runs on the transition into `completed`, and `completed` is in `TERMINAL_STATUSES`; any second `/advance` call on an already-completed booking is already rejected by the state machine (`400 Booking is in terminal status`) before it can reach the ledger write. Confirmed by reading the code, not assumed.

### 19. P1-9 test matrix expansion — DONE (this session)
Went in planning to just write tests for brief §20's uncovered categories (booking status transitions, role permissions, cancellation reversal); found a real, significant money-path bug along the way and fixed it, plus two smaller real gaps.

**The big one — cancellation/completion never released the original allowance hold:**
- `writeReleaseLedger` (provider.ts, fires on reject/cancel) writes a `released` ledger entry, and `writeRedemptionLedger` (fires on completion) writes a `redeemed` entry — but **neither ever reversed the original `reserved` entry from booking creation**. `computeAllowancePosition` (`lib/money.ts`) computed `available = authorized − reserved − redeemed` as flat sums with no netting, so:
  - A **cancelled/rejected** booking's allowance stayed locked forever — the money never came back.
  - A **completed** booking's allowance was **double-deducted** — once as "still reserved," once as "redeemed" — for every single successful booking, permanently.
- This is about as core a bug as this codebase has: it directly undermines "employees get their real allowance back," the product's central promise, on the two most common booking outcomes (finish successfully, or get cancelled).
- **Fix:** `AllowanceEntry` gained an optional `referenceId`; `computeAllowancePosition` now nets `reserved` **per referenceId** (booking) against any `released`/`redeemed` entry sharing that same reference, rather than as one flat aggregate sum. Per-reference netting (not simple aggregate netting) matters because the seed's own hand-authored ledger rows deliberately reference *different, unrelated* bookings for its "reserved" vs. "redeemed" demo rows — a naive aggregate fix would have silently changed the demo's displayed numbers by netting unrelated entries against each other; per-reference netting only resolves entries that actually share a booking, so the seed's numbers are provably unaffected (verified) while the real live-booking code path is genuinely fixed.
- **Found via test-writing, not audit:** the pure-function test suite already had a test titled "release entries do not reduce availability" that only exercised a `released` entry with *no matching `reserved` entry* — which passes under both the old buggy code and the new fix, so it never actually caught this. Writing the *realistic* scenario (`reserved` + `released`/`redeemed` sharing the same `referenceId`) is what surfaced it.
- **Two more call sites had the identical bug independently — a "fixed the shared function" trap:** `GET /v1/employee/overview` (the actual employee dashboard — the single most user-visible allowance number in the whole product) had its **own separate, duplicated inline copy** of the same flawed math that never called `computeAllowancePosition` at all — so fixing the shared library function alone did nothing for the real employee-facing screen. ## Pitfalls
- PGlite data dir parent must exist (`mkdir -p data`); esbuild keeps pglite external; any package importing `@workspace/db` at runtime must declare pglite dep.
- Router-level guards (`router.use(requireX)`) run for unmatched paths too — expect 401/403 on stray URLs.
- Don't name spec component schemas `<OpId>Response` or `<OpId>Body`; use `<OpId>Result`/`<OpId>Input`-style names instead — both collide with orval's own auto-derived operation validator names.
- Changing a query-param shape on an existing endpoint (e.g. adding an optional param) can shift a generated React Query hook's signature from `(options)` to `(params, options)` — always run the *full* `pnpm run typecheck` after any spec change, not just the touched package, to catch call sites this breaks elsewhere in the frontend.
- macOS native binaries: store was built on Linux/Replit; new native deps may need explicit `pnpm add -D <pkg>-darwin-arm64@<exact>` + `pnpm rebuild <pkg>`.
- P1-1: `getSsoConfig()` check runs FIRST in the SSO routes — everything (even bad params) returns 503 until WORKOS_CLIENT_ID/WORKOS_API_KEY/WORKOS_REDIRECT_URI are set. Demo mode is untouched.
- SSO principal types: DB rows have `entryType: string` / nullable `linkedMemberId` — pure functions accept `string`/`number | null` (see `sso.ts` `SsoEmployeeRow`, `money.ts` `AllowanceEntry`); coercions needed when narrowing to `DemoPrincipal` (e.g. `memberId: "memberId" in p ? p.memberId ?? undefined : undefined`).
- `.replit` has NO run config (`runButton = "Project"`) — the two-terminal local dev flow (API :3000 + vite :3001 with `/api` proxy) is the supported way to run the site; the loup-admin app also needs `PORT`/`BASE_PATH` env to build.
- P1-2: `test/tenant-isolation.test.ts` is the first integration-style test (real HTTP via `supertest` against `src/app.ts`, real seeded PGlite data) — unlike every other test file, it is NOT self-contained; it assumes `pnpm --filter @workspace/scripts run seed` has already been run. If tenant-isolation tests fail with unexpected counts/empty arrays, reseed first before assuming a regression.
- P1-4: if the api-server test suite throws a PGlite WASM `RuntimeError: Aborted()` that looks like a fundamental "can't handle concurrent queries" engine limitation, don't trust that diagnosis — first try `rm -rf data/loup-pglite && mkdir data && pnpm --filter @workspace/db run push-force && pnpm --filter @workspace/scripts run seed`. An extensively manually-poked-at local PGlite file accumulated corruption this session and produced exactly that misleading symptom; a fresh store made genuinely concurrent (`Promise.all`) requests pass reliably. See §15 for the full story.
