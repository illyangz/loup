Act as a Principal Full-Stack Engineer and Product Architect. Restructure the existing “Loup” project into an API-first B2B2C employee lifestyle-benefits and service-orchestration platform tailored to the UAE market.

Before making changes:

1. Inspect the existing codebase, database, routes, components and styling.
2. Preserve reusable functionality and the strongest parts of the existing design.

# 1. Product definition

Loup is an employer-funded Life Administration Wellbeing platform.

It helps employers support the part of employee wellbeing that begins outside the workplace: the recurring household, family and personal-administration responsibilities that consume employees’ time and create practical burdens.

Core positioning:

“Loup helps employers give employees time back.”

Supporting position:

“Employee wellbeing does not end when the workday does.”

Loup is not:

* A coupon or discount directory
* A general consumer-services marketplace
* A gym or fitness platform
* A mental-health platform
* A medical platform
* A payroll system
* A bank or stored-value provider
* A generic rewards catalogue

Loup connects employer-authorized benefit allowances with licensed providers of essential life-administration services.

# 2. Wellness framework

Organize the product around four connected wellbeing dimensions:

## Time wellbeing

Reduce the time employees spend discovering, comparing, booking and coordinating service providers.

## Home wellbeing

Support a clean, comfortable, safe and functional home environment.

## Family wellbeing

Allow employees to extend approved support to selected household members and managed dependents.

## Financial wellbeing

Provide employer contributions, negotiated corporate prices and transparent employee co-payments.

Every active product feature must connect to at least one of these dimensions.

Do not make clinical, mental-health, medical, employee-productivity or employee-retention claims.

# 4. Service eligibility framework

Create an internal service-fit model for future category evaluation.

Each proposed service should be scored against:

* Problem frequency
* Estimated personal time saved
* Home-wellbeing relevance
* Family-wellbeing relevance
* Financial value
* Employer relevance
* Repeat-booking potential
* Operational standardization
* Provider availability
* Regulatory complexity

Use the conceptual model:

```text
Service Fit =
Problem Frequency
+ Time Saved
+ Employer Relevance
+ Operational Standardization
+ Repeat Potential
− Regulatory Complexity
```

This model is for internal product planning. It should appear inside the Loup operations interface, not the employee application.

Create a simulated signed-token flow that represents future:

* OAuth 2.0
* SAML

Clearly label the integration as simulated.

## Embedded-widget mode

Create a reusable employee-benefit widget showing:

* Available allowance
* Renewal date
* Eligible services
* Upcoming booking

# 9. Employee checkout

Create a frictionless three-step flow:

1. Select service and service variation.
2. Select address, date, time and instructions.
3. Review pricing and confirm.

The backend must calculate:

```text
Public reference price
− Corporate discount
= Corporate employee price
− Employer allowance contribution
= Employee co-payment
```

Example:

| Component                |  Amount |
| ------------------------ | ------: |
| Public price             | AED 100 |
| Corporate discount       | −AED 10 |
| Corporate employee price |  AED 90 |
| Employer allowance       | −AED 50 |
| Employee co-payment      |  AED 40 |

Allow employees to reduce their allowance contribution but never exceed:

* Available balance
* Category limit
* Per-booking employer limit
* Household allocation
* Benefit expiration rules

Use a simulated saved card and “Simulate Payment” action. Do not collect real payment information.

On confirmation:

* Reserve employer allowance
* Create immutable ledger entries
* Create booking
* Add audit event
* Trigger mock webhooks
* Update employee booking view

On completion:

* Convert reservation to redemption
* Update savings
* Update time-saved estimate
* Update employer aggregate reporting
* Update vendor performance
* Update operational data

# 11. Household access

Allow the primary employee to create a private household group.

Support:

## Invited adult member

* Secure account invitation
* Separate login
* Own private booking history
* Access only to allocated amount and categories

## Managed dependent

* No separate login required
* Managed by primary employee
* Booking details visible to primary employee

The primary employee can:

* Add or remove members
* Allocate allowance
* Restrict service categories
* Revoke unused allocations
* View aggregate household utilization

Rules:

* Household allocations reserve part of the primary allowance.
* No cash moves when an allocation is created.
* Employer funds are redeemed only when an eligible service is completed.
* Allocations cannot exceed available allowance.
* Household members cannot transfer allocations to unrelated users.
* Allocations cannot be withdrawn, sold or converted into cash.
* Allocations inherit the expiration date of the original benefit.
* Household access ends when the employee loses eligibility.
* Employer programme rules override household settings.

The employer must never see:

* Household-member names
* Relationships
* Addresses
* Booking history
* Personal notes
